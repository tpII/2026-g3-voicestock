The access-point script succeeded through these reported steps:

- Access-point capability was detected.
- The AR regulatory domain was verified.
- `wlan0` was selected.
- The `voicestock-ap` NetworkManager profile was created.
- Autoconnect was disabled on the previous Wi-Fi client profile.
- The old client connection was deactivated.

Activation then failed:

```text
Error: Connection activation failed: 802.1X supplicant took too long to authenticate
```

NetworkManager recorded:

```text
Hotspot network creation took too long, failing activation
reason 'supplicant-timeout'
```

Kernel and supplicant lines included:

```text
brcmf_vif_set_mgmt_ie: vndr ie set error : -52

Failed to initialize AP interface
```

working client profile existed:


`802-11-wireless.mac-address`. NetworkManager uses that property as a
device match against the permanent MAC. The interface was using a
temporary locally administered MAC. The permanent USB MAC was
`c0:06:c3:e1:1d:31`. Details are in
[INC-EX-TC-NET-001-20261103-02-02](INC-EX-TC-NET-001-20261103-02-02.md).

The PC script's `require_managed` pattern `10*` was not the exit of this
run. The pattern is still present on `origin/develop` after the Pi-only

### NetworkManager with PMF disabled

The operator modified the existing profile and activated it:

```bash
sudo nmcli connection modify voicestock-ap 802-11-wireless-security.pmf 1
sudo nmcli connection up voicestock-ap
```

With PMF explicitly disabled, the access point activated. Observed:

- `wlan0`: connected
- Profile: `voicestock-ap`
- IPv4: `192.168.50.1/24`
- Mode: AP
- Security: WPA2-PSK
- PMF: disabled

The static IPv4 configuration was verified. The access point had no
gateway, no DNS, and no default route on `wlan0`. Ethernet remained
connected at `192.168.1.100/24`.

The operator cleared the PC MAC restriction:

```bash
sudo nmcli connection modify voicestock-client 802-11-wireless.mac-address ""
```

That removed the MAC-match failure. The WPA2 connection to the
NetworkManager access point still failed.

The Arch supplicant reached:

```text
scanning
authenticating
associating
4way_handshake
disconnected
```

The message recorded as the handshake failure was:

```text
WPA: IE in 3/4 msg does not match with IE in Beacon/ProbeResp
```

The kernel recorded:

```text
Reason: 17=IE_DIFFERENT
```

The two RSN information elements differed.

Beacon/Probe Response RSN IE:

```text
30 14 01 00 00 0f ac 04 01 00 00 0f ac 04 01 00 00 0f ac 02 0c 00
```

Message 3/4 RSN IE:

```text
30 18 01 00 00 0f ac 04 01 00 00 0f ac 04 02 00 00 0f ac 02 00 0f ac 06 0c 00
```

Message 3/4 advertises an additional WPA-PSK-SHA256 AKM suite
(`00-0F-AC:6`) that is absent from the Beacon/Probe Response element,
which advertises a single PSK AKM suite (`00-0F-AC:2`). This record does
not assert that the internal cause inside the Broadcom driver or firmware
has been identified.

The smartphone reported an incorrect password when joining the
NetworkManager-managed access point. That report is consistent with an
authentication failure. It is not evidence that the passphrase was wrong.
Both profiles had been checked against the same configuration file, and
the PSK is not repeated here.

Disabling PMF on the Arch client did not repair the handshake.

This incompatibility is
[INC-EX-TC-NET-001-20261103-02-01](INC-EX-TC-NET-001-20261103-02-01.md).
