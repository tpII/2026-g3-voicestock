## What happened

`sudo bash scripts/setup_pi_access_point.sh wlan0` printed:

```text
ERROR: Wi-Fi interface wlan0 is not managed by NetworkManager.
```

The script stopped. It did not create or activate the VoiceStock access
point.

Immediately afterwards:

```bash
nmcli -g GENERAL.STATE device show wlan0
```

printed:

```text
100 (connected)
```

A device listing still showed:

```text
wlan0  wifi  connected  netplan-wlan0-WiFi-Arriba
```

`wlan0` was managed and connected. The error text did not match that
state.

The check is `require_managed` in `scripts/setup_pi_access_point.sh`, at
the revision under test
(`1b814424b560cafb406ce7069011ba962a5fb82b` on `develop`):

```bash
state="$(nmcli -g GENERAL.STATE device show "$interface_name")"

case "$state" in
  10* | unmanaged* | Unmanaged*)
    error "Wi-Fi interface ${interface_name} is not managed by NetworkManager."
    ;;
esac
```

In Bash, the pattern `10*` matches any string that begins with `10`.
`100 (connected)` begins with `10`, so the connected state takes the
unmanaged branch.

That is a script validation defect. It does not show that the hardware
lacks access-point capability. A separate query,
`nmcli -g WIFI-PROPERTIES.AP device show wlan0`, printed `yes`. The setup
script never reached `require_ap_capable` or `require_regulatory_domain`.
The regulatory lines collected beside this attempt (`country AR: DFS-FCC`
on the first country line, and `country 99: DFS-UNSET` in the per-PHY
section) were not applied by the failed script run.

## Immediate recovery

The access point was not activated. `wlan0` remained on its previous
client connection, `netplan-wlan0-WiFi-Arriba`, at `192.168.1.38/24`.
Ethernet `eth0` stayed up for the SSH session at `192.168.1.100`. No
VoiceStock profile was left active. The PC script was not run.
