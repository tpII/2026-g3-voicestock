# TC-E2E-001 — Simulated Raspberry Pi end-to-end

- Status: DESIGNED
- Executions: none
- Procedure version: 1

## Objective

Run the real `voicestock-pi` runtime from a physical button press through
WAV publication, HTTP upload, contract validation, the operator page, and
both confirm and cancel, with only PC speech-to-text and interpretation
replaced by the deterministic fixture.

## Test level and type

Level: simulated end-to-end.

Type: functional and measurement of the user-observed cycle. Not a full
production end-to-end test.

## Preparation

```bash
mkdir -p recordings/tc-e2e-001
```

Start the fixture. Record its command, its git commit, and a SHA-256 of
`service-success-payload.json`.

Start the Pi:

```bash
VOICESTOCK_PC_URL=http://192.168.50.2:8000 \
VOICESTOCK_PC_TIMEOUT=10 \
VOICESTOCK_WEB_HOST=192.168.50.1 \
VOICESTOCK_WEB_PORT=8000 \
  voicestock-pi \
  --pin <BCM_PIN> \
  --bounce-time 0.05 \
  --input-device "<QUERY>" \
  --output-directory recordings/tc-e2e-001 \
  --catalog <CATALOG_PATH> \
  --keep-recordings
```

Confirm `GET /api/v1/system-status` is `idle` and the page shows
`Listo para escuchar`.

One warm-up cycle (press, wait for the card, cancel on the page) is
discarded from the success rate and from duration summaries. It is still
written in the raw table as `warmup`.

## Execution

Five measured cycles. Cycles 1, 2, and 4 confirm. Cycles 3 and 5 cancel.
That split is the procedure, not a sampled preference.

For each cycle:

1. Start a user-observable timer when the finger presses the button. Stop
   it when the confirmation sentence is visible on the page. This is
   user-observed latency. Keep the watch or the video clock on one
   timeline.
2. Independently, on the Pi, note the monotonic time of the first poll that
   returns `wait_confirmation`. Label that sample API observation latency.
   Do not subtract it from the user-observed number.
3. Check the WAV that appeared in the output directory. Record size,
   SHA-256, and the header format (1 channel, width 2, 16000 Hz). The
   fixture stderr or log should contain the same SHA-256 if the fixture
   was built as specified. If the fixture cannot print a hash yet, record
   **NOT MEASURED** for the server-side hash and still keep the Pi hash.
   The case can pass the byte check only when both hashes exist and match.
   Until the fixture prints the hash, byte equality is **BLOCKED**, not
   passed by assumption.
4. The page shows `Agregar 2 unidades de Arroz Marolio 1 kg`, product
   `Arroz Marolio 1 kg`, operation `agregar`, quantity `2`, unit `unidad`,
   and the synthetic recognized text.
5. Press the button again while the card is visible. The card's operation
   id does not change. `GET /api/v1/pending-operation` still returns that
   id.
6. Confirm or cancel on the page, as assigned above. The page leaves the
   pending card. The API is `idle`, and `pending-operation` is 204.
7. Wait until the status is idle before the next cycle.

After the five cycles, stop the Pi with Ctrl+C and confirm the process
exits. Restart it and run one more press with the fixture still up, to
show a new process can complete one confirm. That restart cycle is extra.
It is not part of the five. If it fails, the case fails. The restart shows
that pending state was only in memory: the new process starts at idle
before the press.

Error recovery is not repeated here. Trial A and trial C of TC-FLOW-001 are
the evidence for stub rejection and an unreachable PC. Cite those execution
ids. Do not reword them as speech-recognition failures.

Do not report a 95th percentile. The sample size is 5.

## Acceptance criteria

1. The peer is the contract fixture. The response that creates the pending
   operation is not `received_audio`.
2. All five measured cycles show the fixture field table on both the API
   and the page, then return to idle by the assigned confirm or cancel
   action.
3. Each cycle's extra press keeps the same `operation_id`.
4. Each kept WAV is a 16 kHz mono 16-bit file with a recorded SHA-256.
   Server-side equality is pass only when the fixture hash is present and
   equal; otherwise that part is **BLOCKED**.
5. The restart cycle starts from idle without the previous operation and
   then confirms one new operation.
6. User-observed and API latencies are both in the summary, not merged.
7. The execution states that real speech-to-text, real interpretation, and
   inventory persistence were not tested.
8. No criterion is marked passed by pointing at
   `tests/integration/test_pi_pc_audio_roundtrip.py` or at CI.

## Failure conditions

- Any measured cycle missing the card, showing a second id, or failing to
  return idle: **FAILED**.
- The stub's rejection message: **FAILED** as the wrong peer.
- Fixture not implemented: **BLOCKED**.
- A pass claim that cites this case as closing PendingOperationWeb-08:
  the claim is a documentation defect. The execution itself stays at its
  product result, and the reviewer rejects that claim.

## Recovery and cleanup

Cancel if a card is still open. Stop the Pi and the fixture. Archive WAV
files and video outside git. Clear `VOICESTOCK_*` exports that were only
for this session if they would surprise the next operator.

## Limitations and exclusions

The spoken words are not the source of the operation. The fixture ignores
them. A successful cycle does not measure recognition accuracy, model
accuracy, or stock movement. Full real end-to-end behavior is a later
campaign. GPIO edge latency and a numeric latency budget remain **NOT
MEASURED** and **TO BE DEFINED**.
