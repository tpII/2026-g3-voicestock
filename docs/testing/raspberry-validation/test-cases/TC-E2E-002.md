## Objective

Show that one physical push-to-talk command on the Raspberry Pi 3 becomes
one validated pending operation and then returns to idle, using the real PC
audio pipeline: Groq Whisper, then `openai/gpt-oss-20b`, then the Pi
validator and the operator page.

The PC server under test is `voicestock-pc-server` with
`VOICESTOCK_AUDIO_PIPELINE=groq`. This case does not use the deterministic
contract fixture. The deterministic simulated case was withdrawn from the
active v0.5.0 campaign before any execution. It is not this path.

## Test level and type

Level: real end-to-end on the project hardware.

Type: functional, negative, and measurement of the user-observed cycle.
Not a speech-to-text accuracy campaign and not an interpretation-accuracy
campaign.

## Execution

Follow [the measurement methodology](../measurement-methodology.md) for an
operator cycle: one warm-up, then five measured cycles. The warm-up is
stored and labeled `warmup`. It is excluded from the success rate and from
latency summaries.

Poll from the Pi:

```bash
curl -sS http://192.168.50.1:8000/api/v1/system-status
curl -sS -D - http://192.168.50.1:8000/api/v1/pending-operation
```

### Positive cycles

Run `warmup`, then P1 through P5, in that order. Wait until the API is
`idle` before the next press.

Each assigned id is one attempt. The first attempt keeps that id and its
result. If the operator presses again after a failed attempt, the new row
is `<id>-extra-<n>`, starting at 1. The original row stays, with its WAV,
API body, and **FAILED** or **BLOCKED** result. An extra row does not
replace it, does not inherit its id, and does not enter the five-cycle
success rate. Do not delete a row, overwrite a hash, or renumber a failed
attempt as the successful one. A later execution id is the only retest.

For each attempt:

1. Start a user-observable timer when the finger presses the button. Stop
   it when the confirmation sentence is visible on the page. This is
   user-observed button-to-pending latency. Keep one watch or one video
   timeline.
2. On the Pi, record the monotonic time from the press until the first
   poll whose phase is `wait_confirmation`. Label that sample API
   observation latency. Do not subtract it from the user-observed number.
   If the runtime does not expose a monotonic stamp for the press, the API
   sample is **NOT MEASURED** for that cycle and the execution says why.
   The user-observed sample is still required.
3. Stop polling when the recorded `VOICESTOCK_PC_TIMEOUT` plus one page
   poll interval (1000 ms) has elapsed and `wait_confirmation` has not
   appeared. That wait is an operator abort. It is not a product budget
   and it is not a latency limit. A cycle that hits the abort fails that
   attempt.
4. Record the new WAV path, byte size, SHA-256, frame count, and header
   fields. The required header is 1 channel, sample width 2, and 16000 Hz.
   Duration is `frames / rate`. Record it. Do not compare it with an
   invented limit.
5. Compare the API body with the assigned row. `product`, `operation`,
   `quantity`, and `unit` must match. `confirmation_message` must be the
   sentence produced from that row by the current view rule. The public
   body does not include `product_id`. The public `product` string is the
   catalog label, so the other presentation fails this comparison.
   `recognized_text` must be a non-empty string and must be the same string
   on the page. It does not have to equal the spoken sentence.
6. Semantic rule for `recognized_text`, applied only as a contradiction
   check. The text fails when it names the other presentation, the opposite
   stock direction, or a different integer quantity. Other wording
   differences do not fail it. Verbatim equality with the spoken sentence
   is not required. Empty text fails.
7. On P5 only, while the card is visible, press and release the button
   again. Poll for five seconds. `operation_id` must stay the same.
   `pending_operation` must still be that one object.
8. Confirm or cancel on the page, as the table assigns. The API returns to
   `idle`, `pending_operation` is null, and `GET /api/v1/pending-operation`
   is HTTP 204. The page no longer shows that card.
9. A second pending id at any time fails the cycle.

P1, P3, and P5 confirm. P2 and P4 cancel. The warm-up cancels so a card is
not left open. The warm-up still has to be written in the raw table.

If the warm-up does not return to idle, do not start P1. The measured set
was not collected. That outcome is **BLOCKED** for the measured rate, and
the warm-up observation stays in the record.

A failed attempt remains in the raw table. The success rate uses only the
first attempt of P1, P2, P3, P4, and P5.

### Negative scenarios

These scenarios are not part of the five. Run them after P5, with the same
processes, once the API is idle. Each id is one scenario and one attempt.
The same no-retry rule applies: a later press is `<id>-extra-<n>` and does
not replace the first result.

N1, ambiguous product. Say a command that names Arroz Marolio and a
quantity, and that does not say `1 kg` or `500 g`. The prepared sentence
is "Agregá dos paquetes de arroz Marolio." Do not add a presentation after
hearing the result.

N2, command the pipeline should not turn into a stock operation. The
prepared sentence is "¿Qué hora es?" Do not repair the sentence inside the
same attempt.

N3, nothing left to confirm. Do not speak. After N2 has been recorded and
the API is idle, read `GET /api/v1/system-status` and
`GET /api/v1/pending-operation` once more, and look at the page. The
expected observation is phase `idle`, `pending_operation` null, HTTP 204,
and no Confirmar or Cancelar card. If N1 or N2 left a card, cancel it,
keep that scenario **FAILED**, and do not start N3 until the API is idle.
N3 does not erase N1 or N2.

N4, recovery. After N3, speak one further add of 1 unit of Arroz Marolio
1 kg. The card must show `agregar`, quantity 1, unit `unidad`, and product
`Arroz Marolio 1 kg`. Cancel it. The API must return to idle and
`pending-operation` must return 204. N4 is not one of P1–P5.

For N1 and for N2, safe behavior is rejection without a pending operation.
Acceptable Pi outcomes are the service-error sentence or the
contract-rejection sentence, with phase `idle`, `pending_operation` null,
and `GET /api/v1/pending-operation` HTTP 204:

```text
La PC no pudo interpretar el pedido. Presioná el botón para intentar de nuevo.
```

```text
El pedido no es una operación válida. Presioná el botón para intentar de nuevo.
```

The transport sentence is not an interpretation result. If that sentence
appears, that scenario is **BLOCKED** because the PC path did not answer.
Do not count it as a successful rejection.

A pending operation on N1 or N2 fails that scenario. Matching the wrong
presentation is not a successful interpretation. Record the public
`product` string that appeared. Cancel the card before the next scenario.
The failed row stays.

#### Where a service error can be seen

The PC returns the structured result inside a successful transport
envelope. `POST /api/v1/interpret-audio` answers HTTP 200. The body has
transport `status` `success`. The inner service object has `status`
`error` and `error.code` plus `error.detail` when interpretation does not
produce a contract. That shape is `ServiceResult` inside
`TransportEnvelope`.

The Pi client parses that body and does not store it. `GET
/api/v1/system-status` copies `operator_message` and `pending_operation`
only. Both rejection sentences above are fixed text. Neither sentence
contains `error.code`. The same service-error sentence is used for every
service failure.

`voicestock-pi` does not configure logging and does not print the
envelope. `PendingOperationFlow` can emit a warning whose text includes
the classified detail, and that detail is built from `error.code` for a
service error. The process does not install a handler, so the warning is
not a required observation. A line that is absent is not a code. Do not
read a code out of the Spanish sentence, and do not invent one.

#### Original response and later replay

The original scenario records the status JSON, the operator sentence, the
pending-operation status, the page, and the kept WAV. Those observations
do not include `error.code`.

To capture the code of the original request, start a capture of the HTTP
response before the press. The capture has to be the response to that
same `POST /api/v1/interpret-audio` between the Pi and
`192.168.50.2:8000`. Extract `payload.error.code` from that body. Archive
the capture outside git as `EV-E2E-002-NEG-<id>-ORIGINAL`. If the capture
was not running, or the body cannot be read, write **NOT OBSERVED** for
the original code.

A diagnostic replay is optional and is a later request. After the original
row is complete, `curl` may post the kept WAV to the same server:

```bash
curl -sS -D - \
  -H "Content-Type: audio/wav" \
  --data-binary @<WAV_PATH> \
  http://192.168.50.2:8000/api/v1/interpret-audio
```

Label that result `<id>-replay`. Record the HTTP status and, when present,
`payload.error.code`. Groq can return a different code for the same bytes.
The replay does not fill the original scenario's code cell and does not
change the original pass or fail. If the WAV was not kept, there is no
replay. Do not fabricate either code.

`ambiguous_product` is not required. `unsupported_command` is one code the
pipeline can emit when no single operation is accepted. Any code copied
from an original response body is the recorded code. A code that appears
only in a replay stays on the replay row.

`ProvisionalOperationExecutor.execute` returns success and does not write
inventory, history, or the resolution. `voicestock-pi` does not take an
executor argument. The execution records that the source at the Pi commit
is that class, and that the launched command did not point at another

extra attempt that reaches Confirm):

- Immediately before Confirm, record the pending-operation JSON, including

- Immediately after Confirm, record the confirm response body and the next

- Immediately before that Confirm and after idle, list files matching
  `*.db` and `*.sqlite*` in the Pi process working directory. Record each

The two listings are evidence about those names in that directory. Equal
listings mean those files did not change. They do not prove that no
inventory mutation occurred anywhere. The check does not read other
directories, other filenames, process memory, or a store the listing
pattern does not name. The source inspection says this executor has no
write. Together, the source statement and the directory listing support
the v0.5.0 claim that this process did not show a database change in its
working directory. They are not a proof of the whole machine.

Then stop the Pi with Ctrl+C and record the exit status when the shell
reports it.

## Acceptance criteria

### Functional acceptance

1. The peer is `voicestock-pc-server` with `VOICESTOCK_AUDIO_PIPELINE=groq`,
   the two required model identifiers, and the campaign catalog. The
   response that creates a pending operation is not `received_audio` and
   is not the synthetic fixture text from
   [fixtures/README.md](../fixtures/README.md).
2. The first attempt of each of P1–P5 reaches one pending operation whose
   public product, operation, quantity, unit, and confirmation sentence
   match the assigned row, on both the API and the page. A later extra
   attempt is not substituted for a first attempt that failed.
3. The first attempts of P1, P3, and P5 return to idle by Confirm. The
   first attempts of P2 and P4 return to idle by Cancel. After each of
   those resolutions, `pending-operation` is HTTP 204.
4. `recognized_text` is non-empty and identical on the API and on the page.
   It is not required to equal the spoken sentence. It fails only when it
   is empty or when it contradicts the assigned presentation, stock
   direction, or integer quantity.
5. P5's extra press does not change `operation_id` and does not create a
   second pending operation.
6. Every kept WAV for those cycles is 16 kHz, mono, signed 16-bit, with a
   recorded SHA-256.

### Safety of operation interpretation

7. No measured positive cycle accepts a different catalog product, a
   different operation, or a different quantity. A wrong match is a failed
   cycle even when the page is internally consistent.
8. The first attempts of N1 and N2 create no pending operation. A guessed
   presentation or an invented stock operation fails that scenario. The
   failed row remains.

### Error handling and recovery

9. The first attempts of N1 and N2 end in `idle` with one of the two
   rejection sentences quoted above, not with the transport sentence.
10. For N1 and for N2, `error.code` is copied from the original response
    body, or the cell says **NOT OBSERVED**. No particular code is
    required. A replay row does not satisfy this criterion. A Pi log line
    is not treated as the code unless the original response body was also
    captured.
11. The first attempt of N3 still shows idle, HTTP 204, and no confirmation
    card. The first attempt of N4 reaches the assigned 1 kg add card and
    then returns to idle by Cancel.

### Evidence completeness

## Failure conditions

The following block a v0.5.0 claim that this case has passed. They do not
rewrite any earlier case.

- The first attempt of any of P1–P5 missing the assigned card, showing a
  second id, or failing to return to idle: **FAILED**. Replacing that row
  with a later press is also **FAILED** as a procedure deviation.
- A positive attempt whose product, operation, or quantity differs from
  the assigned row: **FAILED**. This is a release-blocking interpretation
  failure. The row stays.
- The first attempt of N1 or N2 creates a pending operation: **FAILED**.
  This is a release-blocking safety failure.
- A compared working-directory database listing changes across a
  confirmation: **FAILED** for that observable check. This blocks the
  non-persistence claim for those paths. It is not a certificate that
  every other path was inspected.
- The peer is the stub or a deterministic contract fixture: **FAILED** as the wrong
  peer. Do not relabel the run as a simulated fixture case.
- Required precondition missing: **BLOCKED**. A blocked run does not pass
  the release claim, and it is not a product defect by itself.
- The first attempt of N1 or N2 ends with the transport sentence:
  **BLOCKED** for that scenario. Do not call it a successful rejection.
- Original `error.code` **NOT OBSERVED**: the safety criteria still use
  the public idle state and the absence of a pending operation. Criterion
  10 is met by writing **NOT OBSERVED**. Do not fill the cell from a
  replay, from the operator sentence, or from memory. A replay remains a
  separate row.
- Missing WAV hash, missing commit, or missing launch command: evidence is
  incomplete. The execution cannot be **CLOSED_PASSED**.

Latency above an undefined budget does not fail the case. There is no
approved threshold. Record the samples.

## Recovery and cleanup

Cancel a card that is still open. Stop the Pi and the PC server. Confirm
the Pi pin is no longer held by the process. Archive WAV files, screenshots,
and video outside git. Leave the catalog files in place only if their paths
are recorded. Clear session exports that would make the next operator run
the Groq pipeline by accident, except the key, which stays in its existing
secret store. Do not print the key while clearing the shell.

Do not change application code, the catalog, or the network setup during
the execution and then mark that same execution passed. A corrected rerun
is a new execution id.

## Limitations and exclusions

- This file is a specification. Status remains **DESIGNED** until a
  separate execution record exists. Do not mark this case passed from a
  demonstration, a conversation, or a unit test.
- TC-E2E-001 was a simulated end-to-end specification. It was never
  executed and is withdrawn from the active campaign. This file does not
  change that history into a pass.
- A pass does not measure speech-to-text accuracy and does not measure
  interpretation accuracy beyond the assigned rows and the two negative
  sentences. It does not close InterpretationService-04.
- A pass does not persist inventory. The non-persistence evidence is the
  provisional executor at the recorded commit, the confirm responses, and
  the named listings in the working directory. That evidence does not
  inspect the rest of the filesystem.
- A Pi warning, when it appears, is not a substitute for the original
  response body. A later `curl` of the same WAV is a replay and can differ
  because speech-to-text and interpretation are not deterministic.
- More than one operation in a single command is outside this procedure.
  The pipeline's rejection of that shape is not a measured trial here.
- The informal demonstration on 2026-11-03 is not warm-up, not P1, and not
  N1. It must not be copied into a future execution as if it had been run
  under this procedure.
- GPIO edge latency, a numeric latency budget, and per-stage Groq time
  remain **NOT MEASURED** or **TO BE DEFINED**, as the metrics table says.
